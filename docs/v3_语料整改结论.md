# molecule v3.0 语料整改结论（本轮：做减法，不加源）

> 一句话结论：**formal 硬上限已真正达标（5.57% ≤ 10%）；宽口径（+百科）11.81% ≤ 12% 同样达标；单一来源 ≤0.5% 在当前源结构下
> **数学不可达**（理想下界 5.92%，权重最大的 zh_general 需 87 个独立数据集、现有 17 个），
> 但"不可达"不等于"无事可做"——本轮用**域内均衡**把它从 42.5% 压到域内可控区间，
> 并把"还缺多少源"量化成了可执行的数字。

---

## 一、口径先统一（这是本轮最大的隐性收益）

同一个"来源"有三种粒度，混用会让所有数字失去意义：

| 口径 | 含义 | 例子 | 用途 |
|---|---|---|---|
| `src` | 采样单元（一次抓取批次） | `SkyPile-150B#2020-40_zh_head_0000` | 诊断用 |
| `src_group` | **数据集**（内容供给方） | `SkyPile-150B` | **合规口径** |
| `src_members` | 同一篇内容的转载渠道 | 人民网 / 新华网 / 央视网 各记 1/3 | 跨源去重后计账 |

**硬上限作用在 `src_group`（数据集级）。** 理由：把一个数据集拆成 20 个 shard 就能让每个
都"合规"，那是自欺欺人——真实集中度一点没降。改造前 SkyPile 的 6 个 shard 各自 ~7%
看起来都不超限，合并后是 **40%**，真实风险被完全掩盖。

同时保留 `src` 级数字在报告里（【四】采样单元级），两边都看得见。

## 二、四条硬约束的当前状态（真实全量，32414 篇入池）

| 约束 | 目标 | 实测 | 状态 |
|---|---|---|---|
| 规范书面语（公文+新闻通稿） | ≤ 10% | **5.57%** | ✅ 达标 |
| 宽口径（+百科条目） | ≤ 12% | **11.81%** | ✅ 达标 |
| 单一来源（数据集级） | ≤ 0.5% | 最高 42.5% | ⚠️ **数学不可达**（详见四） |
| 跨源重复 | 先合并再统计 | 精确 111 + 近似 50 + 模板孪生 5 | ✅ 已合并 |
| 高频模板 | 单模板 token 份额 ≤ 5% | 段首复现峰值 31.9% → **7.7%** | ✅ 已压 |

### formal 从 45.57% → 5.57% 的关键：不是"删"，是"稀释"

域内 formal 占比 `f = F/T`。只删 formal 文档 → F 与 T 同减 → `f = (F-x)/(T-x)`：

- `f < 1` 时 f 单调下降（**删得动**）
- `f = 1` 时 f 恒等于 1（**删不动**）

zh_general 域权重 43.67%，池内几乎全是党媒通稿 → `f ≈ 1` → 无论删多少，formal 占比不动。
**唯一的出路是补入非 formal 内容稀释**。这直接决定了本轮的架构：
SkyPile-150B（通用中文网页）不是"又一个源"，而是**稀释剂**。

实测：接入 SkyPile 后 zh_general 域内 formal 从 ~100% 降到 11.1%，
formal 全局占比 45.57% → 5.57%。

### 第 2 条动作的深水区：宽口径曾是 15.83%

formal 达标（5.57%）并不等于第 2 条动作解决了。把 encyclopedic（百科条目体）加进来，
宽口径曾是 **15.83%** —— 正好落在用户预警的 "15%–20%" 区间里。

根因不是"百科源太多"，而是**归类错误**：
`_ENCY_SIGNALS` 里的弱信号（`位于…省`、`字，`）把 SkyPile 的**通用中文网页**
大量误判成百科体 → zh_general 域内凭空多出 6.6% 的百科占比
（encyclopedic 训练流 10.26%，而 encyclopedia 域权重只有 3.67%）。修正后 encyclopedic 训练流降到 **6.24%**，
宽口径落到 **11.81%**（formal 5.57% + encyclopedic 6.24%），在 12% 上限内。

审计报告【二】段现在直接打出 `[宽口径+百科]` 这一行，不用再手算。

误判的代价是双向的：既是"你以为的占比"被凭空做大，
又让这些真实通用网页被当成"高度同质的百科条目"对待 → 误杀多样性。

修正：
1. 百科信号拆成**强/弱**两档，只有明确定义句式 / 条目结构才判 encyclopedic；
2. encyclopedia 域专供百科条目，其他域的"百科腔"不再定性；
3. 新增**宽口径硬上限 12%**（`WIDE_CAP_FRAC`）：压"非 encyclopedia 域"里的百科腔内容。
   encyclopedia 域的 3.67% 是课程指定预算，不可砍（砍了就改了课程配比）。

## 三、本轮新增的"域内均衡"——把不可达变成可控

单源上限不可达时，唯一还能动的杠杆是**域内份额**：

```
训练流占比 = 域权重 × 域内 token 份额
```

`dom_max_group_share = 0.60`（域内单一数据集份额上限），与 formal 上限**联立求解**：

```
均衡目标:  (sT - x)/(T - x) ≤ c        ⟺  x ≥ T(s-c)/(1-c)
formal 约束: w_d · F/(T-x) ≤ f_cap     ⟺  x ≤ T - F·w_d/f_cap
```

两者冲突时只能削到相容点。实测效果：

| 域 | 主数据集域内份额（治理前 → 治理后） | 训练流全局占比 |
|---|---|---|
| code | the-stack-dedup 87.5% → **59.9%** | 20.8% → 14.2% |
| encyclopedia | 分散（33/33/33） | 1.2% each |
| math_reason | NuminaMath 97.4% → 89.9% | 10.5% |
| zh_general | SkyPile 97.2%（**不动**） | 42.5% |

**zh_general 为什么不动**：formal 上限把均衡目标锁死在 94.2%
（域权重 43.67% × 域内 formal ≤ 22.9%），削 4.3M token 只换 3 个百分点 →
**纯浪费**（token 不会凭空变成别的源，只是让域变小）。加了收益判据
`MIN_BALANCE_GAIN = 0.15` 自动跳过。

## 四、单一来源 ≤0.5% 为什么不可达（量化到"还缺多少"）

**下界推导**（pigeonhole）：域 d 权重 `w_d` 固定，域内 `n_d` 个独立数据集，
任一数据集的域内份额 ≥ `1/n_d` → 其训练流占比 ≥ `w_d / n_d`。

| 域 | 域权重 | 现有独立数据集数 | **达标所需** | 缺口 |
|---|---|---|---|---|
| zh_general | 43.67% | 17 | **87** | −70 |
| code | 23.67% | 4 | **47** | −43 |
| math_reason | 11.67% | 7 | **23** | −16 |
| book | 10.67% | 3 | **21** | −18 |
| en_general | 6.67% | 6 | **13** | −7 |
| encyclopedia | 3.67% | 4 | 7 | −3 |

全局理想下界 = **5.92%**（`max_d w_d/n_d`），是硬上限 0.5% 的 **12 倍**。

**这不是算法 bug，是源结构问题。** 三条路：
1. 补真正独立的内容源（每个中文源至少 ~10 万 token 才有效）
2. 降 zh_general 域权重（但课程配比是固定的）
3. 接受它，并保证**没有任何单一数据集能靠"多 shard"伪装成多源**

本轮选了 3，并把"还缺多少"量化进报告，让下一次补源有明确靶子。

## 五、发现的一个新问题：域重复率（比集中度更该先看）

```
重复率 = 训练流分给该域的 token ÷ 池子里实际有的
```

| 域 | 池内 token | 需喂（100B × 域权重） | 重复率 |
|---|---|---|---|
| book | 18,293 | 10.7B | **583,101×** |
| encyclopedia | 29,100 | 3.7B | 126,002× |
| code | 180,239 | 23.7B | 131,307× |
| math_reason | 210,076 | 11.7B | 55,536× |
| zh_general | 7,888,482 | 43.7B | 5,535× |
| en_general | 11,165,849 | 6.7B | 597× |

**这是当前抽样规模的诊断，不是语料本身不足**（CI 每源只抓几 MB）。但它推翻了
"继续删"的直觉：**在真实全量语料到位前削 token，只会把重复率推得更高。**
所以本轮的"删"全部限定在**去重与模板污染**（删的是重复内容，不是独立内容），
配额裁剪只压 formal 与域内集中度，不做无差别瘦身。

## 六、本轮改动清单

### `corpus_govern.py`（新增，核心）
- `minhash_lsh_dedupe()`：64 维 MinHash + 4band×16row LSH，跨源近重复
- `template_dedupe()`：**源内**模板去重（跨源去重看不见"同模板反复生成"）
- `enforce_caps()`：token 口径配额求解，**数据集级**上限
  - `dom_balance_plan()`：均衡目标与 formal 上限联立求解
  - `exclusive_dom_share()`：域独占强制下界（"这个源删不掉的最低占比"）
  - `dom_feasible()`：域级可行性预检（避免白砍）
  - `can_delete()`：域地板 + 域非空 + **动态**稀释底座三重保护
- `compute_shares()`：`src_group` 两级口径 + 逐域 formal 稀释诊断 + 域重复率

### `build_corpus_v3.py`
- `build_global_pool()`：`src_group` 字段贯通
- `collect_modelscope()`：ModelScope 层（SkyPile 作稀释剂）
- 治理流程接入 `template_dedupe`（在配额裁剪**之前**——先删模板污染再算配比）

### `modelscope_corpus.py`
- `the-stack-v2` → **`the-stack-dedup`**（前者镜像只有元数据无 content 列）

### `tools/test_corpus_govern.py`（9/9 通过）

T9 宽口径上限达标且 encyclopedia 域不被砍空

### 语料配方版本戳（防"代码改了但语料没换"）

## 七、下一步（按性价比排序）

先说结论：**现在该停手。** 用户的判断是对的——语料工程的边际收益掉得非常快，
100B 的预算连现有这些源都吃不完（当前池子离 100B 差几个数量级，见第五节重复率诊断）。
所以本轮的"删"已经把能删的都删了：重复的、模板污染的、超配比的。
**接下来真正的瓶颈是"量"，不是"源的数量"。**

| 优先级 | 动作 | 性质 | 理由 |
|---|---|---|---|
| 1 | **扩大量而非加源**：把现有源抓取量放大 10²–10³ 倍 | 加量 | 重复率 583,101× 是当前硬伤；把量做上去，单源集中度的**绝对**影响同步被稀释 |
| 2 | 补 zh_general 的独立中文源（每源 ≥10 万 token，按批补） | 加源 | 唯一能实质降集中度的动作，但边际收益递减，按批补、不专项攻坚 |
| 3 | 补 code 域独立源（需 47 个，现有 4 个） | 加源 | the-stack-dedup 全局 14.2% 是第二大风险，但同样受边际收益约束 |
| 4 | **不再在配额求解器上加规则** | 停手 | 治理层行为已可解释：要么达标，要么如实报告做不到、以及还缺什么 |

已经停手的地方（明确不做）：
- 不再做无差别瘦身——削 token 不会让 token 变成别的源，只会推高重复率；
- 不把数据集拆成多 shard 来"满足"单源上限——那是自欺欺人；
- 不改课程配比来"解决"集中度问题——降 zh_general 权重虽然能让数字好看，
  但那是改题目不是做语料。
