# v3.0 训练链路修复纪要（2026-11-02）

> 一句话：**训练链此前从未真正跑起来过。** 表面看是"每轮都在跑、loss 也在降"，
> 实际上每一轮都是从零开始训练——抗取消持久化从未生效，10 天发版闸门永远攒不满。
> 本轮定位并修复了这条链上的 3 个 P0/P1 级故障。

---

## 一、故障全景

| # | 故障 | 症状 | 根因 |
|---|---|---|---|
| P0-1 | 抗取消持久化从未执行 | 滚动发布 `v3-checkpoint` **从未存在**；每轮日志都是"无滚动检查点（首轮），从零开始训练" | `persist_v3.py` 守卫查 `GITHUB_TOKEN`，CI 注入的是 `GH_TOKEN` → 第一行就 return |
| P0-2 | 周期存档的持久化被回收 | CI 跑过 30 分钟（2 个存档点），滚动发布资产时间戳纹丝不动 | 周期存档走 `Popen` 异步 fire-and-forget；CI 回收 run 时父进程先退，子进程在 320MB 上传完成前被一起收走 |
| P1-1 | 发版闸门只看时钟不看质量 | 训练崩了（PPL 爆炸 / NaN）也会攒满 240h，照样发 v3.0 | 闸门只判 `HOURS >= 240` |

三者叠加的后果：**10 天时钟长期停在 1.25h / 240h**——不是训练慢，是每轮都在归零重来。
按当时每轮 75 分钟算，攒满 240h 需要约 192 轮 × 75 分钟 ≈ 10 天；但因为每轮归零，
**永远攒不满，v3.0 永远发不出来**。

## 二、修复内容

### 1. `persist_v3.py`——token 变量名

```python
# 修复前：CI 注入的是 GH_TOKEN（gh CLI 认的名字），这里查 GITHUB_TOKEN → 永远 None
if not os.environ.get("GITHUB_TOKEN"):
    return

# 修复后：两个名字都认，并显式注入 gh 子进程环境
token = os.environ.get("GH_TOKEN") or os.environ.get("GITHUB_TOKEN")
if not token:
    return
gh_env = dict(os.environ)
gh_env["GH_TOKEN"] = token
```

### 2. `train_v3.py`——持久化改同步

```python
# 修复前：周期存档异步
persist()   # Popen fire-and-forget

# 修复后：统一同步阻塞
persist(block=True)
```

代价：每 `save_every`（10）分钟阻塞约 1–2 分钟（上传 ~90MB）。相对单轮 75 分钟完全可接受。

### 3. `ci_v3.yml`——双持久源 + 质量门

- **Resume 兜底**：滚动发布不可用时，从上一轮成功 run 的 `resume-v3` artifact 恢复
  checkpoint + 时钟 + 语料。artifact 是第二持久源，能兜住"单点失效"。
- **artifact 补齐**：`resume-v3` 原先只传 `checkpoints/`，时钟根本没进 artifact
  （兜底也救不回来）→ 补上 `data/v3_clock.json` 与 `data/v3_midtrain.bin`。
- **发版质量门**：读 checkpoint 的 `ppl` 字段，要求 **PPL < 10**（设计目标）才发版；
  拿不到 PPL（checkpoint 缺失/损坏/非有限值）按**不达标**处理——宁可不发，不发废模型。
- **死锁修复**：EXIT trap 的续训守卫原为"到量即停训"。但质量门可能拦住发版 →
  trap 也不续训 → **没人发版也没人继续训**，链条死锁。
  改为"**到量 且 PPL 达标**才停训"；质量不达标则继续训到达标为止。

BPE / 配方戳。**这是修好之前从未存在过的东西。**

### 本地训练链路端到端跑通

```
[build] 复用已有 v3_*.bin（20649728 seqs，seq_len=256，配方版本 2026-11-02.3 匹配），跳过构建
[model] v3 基础模型参数: 79.9M（15 组权重共享，纯骨干）
[step 1] loss=11.612 (lm=8.924 mtp=8.932) ppl≈7509.24

[stop] 软时限 6 分钟到，优雅停止 @ step 15
[done] checkpoint -> checkpoints/v3.pt | 本轮 6.3 分钟
```

### 线程数实测（本地 32 核，意外发现）

| 线程数 | 吞吐 |
|---|---|
| 1 | 挂起无输出 |
| 2 | 79.5 tok/s |
| 3 | 87.4 tok/s |
| **4** | **116.1 tok/s** ← 最优 |
| 6 | 102.0 tok/s |
| 8 | 89.1 tok/s |
| 16 | 41.9 tok/s |
| 32 | 超时无输出 |

**线程越多越慢**，4 线程反而比 16 线程快 2.8 倍。原因：Mamba 线性递推 + BinaryAttention
以小矩阵运算为主，线程同步/调度开销压倒计算量，线程一多就互相抢。
CI 的 `OMP_NUM_THREADS=4` 恰好落在最优点——保留不动。

### 训练预算核算

实测吞吐 5.14 步/分（CI 4 线程），每步 4×256 = 1024 token：

| 指标 | 数值 |
|---|---|
| 240h 总步数 | ≈ 74,000 |
| 240h 总 token | ≈ 80M（0.08B） |
| 需跑轮次 | ≈ 192 轮（75 分钟/轮） |
| 当前语料池 | 20.6M token |
| **语料够喂 240h？** | **够**（覆盖率 27%，设计上是 3–4 epoch 多轮） |

但注意域重复率差异极大：`book` 域只有 472 条 seq 会被重复约 60 次，
而 `zh_general` 有 32,532 条 seq 只重复约 3.6 次。
这是"补量优于补源"结论的量化依据。

## 四、教训

1. **"在跑"不等于"在积累"。** 每轮 CI 都是 `success`，loss 曲线也正常下降——
   但每轮都是从零开始。**指标必须看累计量（时钟），不能看单轮表现。**
2. **环境变量名是最容易被忽略的静默故障点。** `GITHUB_TOKEN` vs `GH_TOKEN` 只差一个字母，
   效果是整个持久化机制静默失效，且**不报错、不失败**——脚本正常退出，CI 显示绿色。
3. **异步 ≠ 可靠。** 在"进程随时可能被杀"的环境里，fire-and-forget 是反模式。
   需要落库的关键动作必须同步等待。
4. **单点持久化必须配兜底。** 滚动发布 + artifact 双源，任一失效链不死。
5. **闸门要校验质量，不只校验数量。** 攒够 10 天 ≠ 模型能发。
